**一、文件目的**

本文件用來定義 LOHAShare AI Platform 文件內容品質、閱讀友善性、邏輯一致性與整編方式。它不是用來替代既有文件，而是作為未來文件稽核、補正、v2.0 Clean Version 整編與 AI 文件審查的共同判斷標準。

本文件的核心任務，是避免正式文件變成一塊一塊的補丁；補正可以作為過程，但正式交付文件必須重新整編成可閱讀、可執行、可追溯的 Clean Version。

**二、核心原則**

| **原則**                                    | **規則說明**                                                                                 |
|---------------------------------------------|----------------------------------------------------------------------------------------------|
| 補正是過程，整編才是交付                    | 文件可先用稽核表與補正清單追蹤缺漏，但正式文件不應堆疊補丁；應重新安排章節與敘事動線。       |
| 不摘要化導致內容遺失                        | 若前文已形成完整策略、判斷邏輯、適用情境、不適用情境、風險邊界，正式文件不得只保留簡短結論。 |
| 先維持主軸，再處理細節                      | 主 PRD、架構治理、自動化策略、模組規格、Support Log、Prompt 各有不同層級，不得互相取代。     |
| Clean Version 要乾淨，Correction Log 要完整 | 正式文件保留閱讀友善性；缺漏、偏差、舊版錯誤、補正理由應放入稽核與補正紀錄或附錄。           |
| AI 可協助審查，但不可直接定稿               | AI 可提出內容品質問題與重整建議；Stable 文件必須經人工審核確認。                             |

**三、文件內容品質的六個檢查面向**

| **面向** | **檢查問題**                                                                                      | **常見錯誤**                                            |
|----------|---------------------------------------------------------------------------------------------------|---------------------------------------------------------|
| 層級定位 | 文件是否清楚區分 Level 0 平台、Level 1 主 PRD、Level 2 MVP、Level 3 模組、Level 4 衍生文件？      | 把 Nexus Lead Ops 寫成主 PRD；把 POC 寫成正式產品主線。 |
| 完整性   | 是否保留策略主軸、判斷邏輯、適用情境、不適用情境、風險提醒、執行順序？                            | 只剩摘要條列，缺少為何這樣做與何時適用。                |
| 閱讀動線 | 讀者能否從背景、定位、規則、執行、例外、版本沿革順序理解？                                        | 補充段落散落各處，像貼補丁。                            |
| 一致性   | 用語、版本、資料夾位置、命名層級是否與 Current Folder Structure / New Conversation Handoff 一致？ | 同一文件中同時出現不同版本命名或不同正本位置。          |
| 可執行性 | 文件是否能轉成任務、檢查表、Manifest、Prompt、SOP 或 GitHub Actions 驗收規則？                    | 只有概念，沒有下一步、負責角色、產出物與驗收標準。      |
| 可追溯性 | 是否保留版本沿革、修正理由、廢止說法與決策紀錄？                                                  | 為了閱讀乾淨而刪光修正背景，未來無法追溯。              |

**四、正式文件不得出現的問題**

- 不得把補充、修正、再次修正、前版錯誤修正直接堆在正文，造成閱讀斷裂。

- 不得把對話中完整形成的策略主軸壓縮成過度簡化的幾行摘要。

- 不得把 Level 3 模組或 Level 4 衍生文件寫成 Level 1 主 PRD。

- 不得把 Support Ticket、Fallback POC、Developer Prompt、Test Log、SOP、Release Note 寫成主產品本體。

- 不得讓自動產出文件直接成為 Stable；必須標示 Draft Generated / Reviewed / Stable。

- 不得在文件中同時使用已廢止與新確認的資料夾結構，除非是在「廢止說明」或「修正對照」中。

**五、v2.0 Clean Version 整編規則**

當 v1.x 文件經歷多次補正、命名修正、內容補回或架構調整後，應進入 v2.0 Clean Version 整編流程。v2.0 不是單純新增段落，而是以最新正確理解為基準，重新組織正式文件正文。

| **整編項目** | **處理方式**                                                            |
|--------------|-------------------------------------------------------------------------|
| 章節重排     | 依照「目的 → 定位 → 架構 → 規則 → 流程 → 例外 → 驗收 → 版本沿革」重排。 |
| 內容補回     | 把被摘要化的策略、判斷邏輯、適用情境與風險邊界補回主文或附錄。          |
| 重複合併     | 同一概念多次出現時，整理成一個正式章節，避免多處不同說法。              |
| 補正痕跡移位 | 正文保持乾淨；錯誤更正、舊版偏差與對照表移到附錄或 Correction Log。     |
| 版本歷程保留 | 保留 v1.x 探索與補正紀錄，但不讓歷史錯誤干擾正式閱讀。                  |
| 人工審核     | v2.0 Clean Version 產出後，必須由使用者確認後才標示 Reviewed / Stable。 |

**六、補正內容的放置位置規則**

| **內容類型** | **放置位置**                            | **說明**                                                |
|--------------|-----------------------------------------|---------------------------------------------------------|
| 正式規則     | 正文                                    | 已確認且未來要遵守的規則，應整合到合適章節。            |
| 補正原因     | Correction Log / 附錄                   | 說明為何修正、原本哪裡偏差、如何修正。                  |
| 舊版錯誤說法 | 附錄：已廢止用語                        | 只保留作為避免再犯的對照，不放在主文。                  |
| 測試與截圖   | 02_Modules 或 04_Support_Knowledge_Base | 依文件性質歸檔，不放入治理文件正文。                    |
| Prompt 正本  | 05_Developer_Prompts                    | Prompt 可在模組文件中引用路徑，但正本不放入模組資料夾。 |
| Release 摘要 | 06_Release_Notes                        | 正式發布或階段成果用 Release Note 管理。                |

**七、文件稽核時的標準問題**

1.  這份文件的層級是主 PRD、架構治理、模組規格、SOP、Support KB、Prompt，還是 Release Note？

2.  文件是否曾把 Nexus Lead Ops / Lead & Notification Console 寫成主 PRD 或平台母體？

3.  文件是否有被摘要化，導致原本的策略邏輯、風險提醒、適用情境消失？

4.  文件中是否有與 Current Folder Structure v1.2 / 後續最新版不一致的正本位置？

5.  文件是否包含補丁式段落，讓讀者必須自行拼湊邏輯？

6.  這份文件是否應進入 v2.0 Clean Version 整編？若是，應保留哪些內容、移除哪些重複、搬移哪些補正紀錄到附錄？

7.  文件產出狀態是 Draft Generated、Reviewed、Stable，還是 Deprecated？

**八、AI 文件審查與人工審核流程**

未來使用 ChatGPT、Claude、Codex、Gemini 或其他 AI 工具進行文件審查時，應先引用本文件作為內容品質標準。AI 可協助找出問題、提出整編建議、產生 v2.0 草稿，但不可直接覆蓋正式文件。

| **步驟**     | **角色**            | **產出**                                                  |
|--------------|---------------------|-----------------------------------------------------------|
| 1\. 文件盤點 | 使用者 / AI         | 列出待審文件與版本。                                      |
| 2\. 內容稽核 | AI 輔助             | 找出摘要化、定位偏差、閱讀斷裂、資料夾不一致等問題。      |
| 3\. 補正清單 | AI 輔助，使用者確認 | 形成 Audit and Correction Log。                           |
| 4\. 整編草稿 | AI 輔助             | 產生 v2.0 Clean Version 草稿。                            |
| 5\. 人工審核 | 使用者              | 確認內容是否正確、完整、可閱讀。                          |
| 6\. 正式升版 | 使用者 / AI 輔助    | 更新 Document System Index、Release Note 與相關治理文件。 |

**九、與現有治理文件的關係**

| **相關文件**                           | **關係**                                                               |
|----------------------------------------|------------------------------------------------------------------------|
| Current Folder Structure               | 定義資料夾與正本位置；本文件負責內容品質與整編規則。                   |
| New Conversation Handoff               | 定義跨對話同步基準；本文件補充新對話中如何避免內容摘要化與定位偏差。   |
| Document System Index                  | 列出正式文件與版本；本文件協助判斷哪些文件需進入 v2.0 整編。           |
| Document Audit and Correction Log      | 記錄稽核結果與補正狀態；本文件提供稽核判準。                           |
| Document Consolidation Plan            | 規劃整編順序與 Clean Version 策略；本文件提供內容品質規則。            |
| Automation Strategy and DocOps Roadmap | 定義自動化策略；本文件確保自動化產出的文件仍具閱讀友善性與內容完整性。 |
